## 4 契约冻结流程

只冻结当前纵向闭环真正用到的最小集合，不要求先设计完所有未来功能；任何未冻结依赖不能靠实现者自造DTO、表或状态补齐。

冻结包至少包含：
1. 适用C/FR/V及已接受ADR、负责人与受影响消费者。
2. 稳定ID、所有者/操作者/小组/绑定区别，必填、缺省、null、空数组和更新语义。
3. 媒体源区间、切片局部时间、时间线位置、单位、帧舍入和版本规则。
4. 请求/响应、命令/事件、错误到界面及重试行为，幂等作用域、同键异载荷处理。
5. 状态转换表：当前状态、触发、唯一写入责任、权限/人工批准、原子条件、结果证据、恢复及显示。
6. 物理存储映射、约束、迁移唯一负责人、文件与记录不一致的恢复办法。
7. 正例、反例和跨语言相同样例，以及支持/拒绝的版本组合。
8. 变更影响、兼容窗口、迁移/前向修复及验收记录。

拟定生命周期：提出 → 业务与消费者评审 → 样例验证 → 冻结版本 → 实现 → 兼容变更或显式替代。冻结意味着有具体可引用版本和批准记录，不是把讨论文档标题改成“正式”。

业务确认后仍需单独批准相关验证/实现范围；本轮不生成Schema或运行样例。将来机器契约与07同次变更，自动检查生成物一致、运行时校验及跨语言序列化。只共享TypeScript类型而不校验IPC/worker输入不算契约统一。

跨模块变更先登记影响，再由契约负责人统一修订及补样例，相关消费者审查；优先兼容增加，消费者迁移后再按版本规则移除旧项。不兼容变更必须有明确版本、处理旧客户端的方案和迁移证据。只有受影响任务暂停/更新基线，无关任务可继续。不得私发临时字段、偷偷容忍未知状态或修改黄金样例来掩盖违约。

### 4.1 冻结权限与两阶段就绪

以下为工程责任提案，实施授权时登记真实负责人：
- Ethan负责业务范围、风险容忍度及其变更；已授权范围内的纯工程取舍由技术负责人提出ADR并负责。
- 契约负责人维护唯一注册表、版本与变更包，不单独替所有消费者批准。每个受影响的生产者/消费者由其负责人或预先登记代理给出明确结论；缺席、异议未解决或证据不足，保持未冻结。
- 技术负责人在上述意见和非作者审查齐全后签发技术冻结/兼容变更；提案作者不能作为唯一批准人。冲突涉及业务时交Ethan，纯工程分歧由技术负责人说明取舍和影响后裁决，但不能豁免未满足的硬验收。
- 身份/权限、积分账务、数据迁移、外部数据流和发布的高风险变更，还须具名的人类技术负责人批准；未指定人时由Ethan决定授权谁，不以Agent自批代替。

区分两种记录：设计冻结确认语义/样例与责任，允许在另获授权后实施契约基础任务；可消费冻结才表示机器Schema、运行时校验、生成物、正反样例及兼容测试已形成同一可引用提交。业务消费者任务须引用后者，不能拿设计稿就绪冒充可消费版本。首次机器契约由单写者基础任务产生，不要求业务模块先各自造实现才能冻结。

冻结后不原地解冻同一版本：提出变更单、新候选版本及影响清单，沿同一审批链发布替代版本；旧版本按兼容策略保留。冻结记录包含签发者、各方结论、基线提交、契约摘要/版本及状态，所有任务引用同一个登记。

## 5 模块所有权和数据写入责任

以下是领域责任地图，实际目标路径和依赖白名单统一见[13技术架构与目录依赖基线](13_技术架构与目录依赖基线.md)；任务卡再映射到获准隔离工作树，不另列竞争结构。每一工作包同一时刻只有一个实现负责人，变更负责人必须有交接记录。

| 模块 | 唯一负责的领域行为 | 禁止越界 |
| --- | --- | --- |

| 超级混剪 | 配方、冻结选材、批次规划、组合准入和结果关联 | 改组序、私自释放未知占用、直接写编辑器内部存储 |

| AI与积分 | 统一模型调用、输出验证、成本和账号积分账 | 按HTTP成功直接扣分、把供应商成本等同用户积分、向日志写原始输入/密钥 |

| 任务与观测基础 | 工作协议、尝试/取消/恢复、统一追踪及审计接口 | worker自行推进其他领域终态；日志替代业务账本 |

每个聚合/状态仍须在冻结包明确唯一写端：worker报告执行事实，本地负责人核验文件事实，可信服务掌握共享准入/积分等服务事实；三者不是互相覆盖的同一状态列。

公共契约、身份授权、数据库迁移、根依赖/锁文件、CI规则、公共验收样例分别登记单写者。并行并不允许多位Agent各自编号迁移或编辑同一共享基础。依赖方向与禁止的内部导入由自动检查保障；仅有目录名不构成隔离。

## 6 任务卡和交付协议

任务卡是每个实现者的唯一任务授权包，不粘贴整段聊天历史。任务卡由总控登记，修改范围或验收须留下变更记录，不能由功能实现者单方放宽。

| 字段 | 必填内容 |
| --- | --- |
| 身份 | taskId、任务目标、负责人Agent ID、模型与reasoning_effort、选择理由、授权边界 |
| 基线 | baselineCommit、PRD/C/ADR引用、契约版本、依赖任务及可用的样例版本 |
| 工作区 | 绝对worktree路径、唯一分支、当前工作目录；实现前自检实际路径/分支 |
| 修改范围 | 允许写入路径、禁止写入路径、共享文件负责人、允许的外部动作 |
| 接口 | 输入输出、状态/错误、权限、幂等和兼容性要求，生产者与消费者 |
| 验收 | 正反用例、必需执行项目、证据位置、未覆盖部分、恢复方案 |
| 资源 | 测试数据库/命名空间、端口、临时输出、缓存、GPU/剪映实测占用规则 |
| 调度 | 所需依赖提交/契约包、当前ready证据、任务级N5a适用记录、占用/释放、审查等待及并发调整原因 |
| 停止条件 | 业务歧义、未冻结契约、权限扩大、越界改动、无法隔离、破坏性动作、缺必要凭据 |
| 交付 | 提交范围、实际文件差异、执行记录、审查结论、风险和剩余阻塞 |

任务生命周期建议为：待澄清 → 就绪 → 已认领 → 实现中 → 待审查 → 待集成 → 已验证；阻塞、取消和需修订单独记录。“已认领”仅表明唯一执行者，不代表内容获准；“Agent完成”不是“已合并”或“已发布”。

实现者只交付自己范围内的改动，不修改其他Agent正在工作的目录、不替别人提交，也不擅自创建子Agent。总控统一派发独立审查，避免重复审查和无界扇出。上下文压缩/恢复后先读任务台账、实际提交和未决状态，不凭聊天记忆重复派发已完成工作。

### 6.1 任务交接与基线前移

单写者交接由总控执行：先停止旧执行者并确认不再写入，冻结其分支/工作树状态，记录原始提交、未提交差异、样例结果和未完成项；不得丢弃差异或把旧贡献改署新作者。随后更新任务负责人及assignmentRevision，使旧卡失效，再将接续范围和证据交给新Agent确认接收。无法确认旧任务已停止时不在同一写集启用新实现者；可先做只读诊断。旧Agent恢复后必须检查当前登记，过期卡禁止交付/合入，即使旧工作树还可写也不被集成接受。

原始baselineCommit永久保留用于追溯；新增workingBaselineCommit和integrationCandidateCommit记录换基和拟合入结果，不覆盖原记录。总控依据契约消费者清单、模块依赖图和实际差异判定受影响任务并下发新卡版本；影响未知的消费者先按受影响处理。未受影响任务可继续，受影响任务由原实现者适配后重新报告。

审查/测试证据绑定实际PR头提交、依赖版本和集成目标头（或实际候选合并提交）。代码、契约、关键依赖或集成头改变时，原证据不能直接冒充新组合通过；按依赖影响清单重跑必要检查并重新审查受影响差异。未变部分可引用可核验的旧证据，但不得复用已经过期的整单批准。旧头的绿色状态不能授权新头合入。

## 7 Superpowers 模型分级和并行边界

核对依据是本机安装的Superpowers 7.0.1，不假定未来版本不变：
- subagent-driven-development（使用当前工具提供的同名技能）的Model Selection要求按任务难度/风险选模型，并明确禁止同一SDD流程同时派发多个实现者。
- dispatching-parallel-agents（使用当前工具提供的同名技能）用于独立、无共享可变状态的工作；相关任务或写同一文件不适合直接并行。
- Codex适配说明（使用当前工具提供的同名技能）要求干净上下文，并显式指定model及reasoning_effort；以实际运行时工具允许列表为准。

| 任务类型 | 路由原则 |
| --- | --- |
| 完整规格、机械性、单文件或少量明确修改 | 能胜任的轻量快速模型；不能因单文件就忽略权限/账务风险 |
| 文字规格、多文件集成、定位问题、一般任务审查 | 标准能力模型；不盲目用最便宜模型换取更多返工 |
| 架构、复杂并发/权限/迁移、最终全分支审查 | 运行时允许的最高能力档；reasoning_effort匹配实际难度 |
| 小修复的定向复审 | 按实际差异缩小模型档位与上下文 |
| 持续失败的修复 | 按技能修复循环执行升级/中止规则，不无限重复同档尝试 |

每次派发记录实际model、reasoning_effort、Agent ID、任务及成本/耗时证据，不固定写死模型别名、价格、供应可用性或把高档等同永远最高推理。最终审查的能力档不能因继承默认值而无意降低；模型升级不能授权扩范围。开发Agent成本与产品用户的模型积分不是同一本账。

### 7.1 C89动态并发及技能适配

Ethan已明确批准项目级动态并发，替代先前固定实现者数量和M1后才并行的建议。这是对SDD默认“不并发派发实现者”的明确项目级调整，不是声称技能原文已改变。总控用dispatching-parallel-agents协调独立工作包；每包仍执行SDD的任务上下文隔离、测试、独立规格/质量审查和修复循环。不会让多个SDD流程同时写同一台账或同一工作区；单包内部存在顺序依赖时仍按顺序实现。

可同时实现的前置条件：
1. 已批准的实施计划/任务范围，且不是仅有PRD或讨论稿。
2. 消费的契约包达到consumer_ready，所需最小运行端口/前置产物已落在可引用提交；尚未实现的依赖只能用于明确标识的替身适配任务，不能标整链通过。
3. 每位写入者有独立工作树/主题分支、唯一任务卡和不重叠的允许写集；共享文件由登记的单写者维护。
4. 外部权限、测试数据、端口/数据库/文件/硬件资源满足隔离，容量可用。
5. 11的N5a在本次首次并发写入前通过，且适用于当前写集/契约/工具版本；新范围或门禁改变需重验受影响项。

最初HIST-T01/HIST-T02的环境、契约及门禁引导可按单写者顺序建设；不要求门禁在自身尚未实现前证明通过。受影响消费者就绪即可独立放行，不等待所有K包、整个M0或M1；必须依赖的部分仍等待。只读调研无需等写入准入，但仍遵守权限/共享桌面排他限制。

### 7.2 总控调度与背压

总控维护一个项目级任务索引；每个执行包有独立进度记录。登记planId/taskId、工作树、assignmentRevision、依赖提交、契约/fixture版本、读写范围、资源、状态及审查证据。就绪不等于已验收；多个包的局部绿色不得合成整链绿色。恢复会话先读台账及实际Git，不凭聊天重复派发。

每次任务完成、出现审查/修复、依赖更新或资源变化时：
- 先更新ready集合；被未冻结依赖、权限或资源阻塞的任务不派发实现，只能做获准的只读准备。
- 优先消化阻塞关键路径的审查、修复和集成；再选择无冲突的就绪任务填充空槽，不为空闲审查者永久预留槽。
- 运行中实现者数量受实际总槽位扣除总控及其他活跃角色、独立就绪任务数和资源预算共同限制；这是容量上界，不是必须跑满的目标。
- 有待审成果时，将下一个可用槽优先分配给新的非作者审查者；不得持续启动新实现让审查饥饿，也不因满槽允许自审自合。所有实现者忙时等待安全交接点/完工释放槽，不强杀造成未保存成果丢失。
- 审查积压、返工、集成冲突或硬件争用上升时减少新任务派发，保留成果后收敛根因；恢复扩并发须有证据和调度记录。

示例仅说明容量：若运行时提供总计4槽且总控占1槽，无待审且3项均独立就绪时可派发3个实现者；产生待审后可转为2个实现者加1个新的审查者。若运行时容量不同则重新计算，不将2/3/4写成永久项目上限；嵌套派发不突破实际工具额度，实现者不得无界扇出。

观察指标以通过验收的交付/集成耗时为主，并记录审查等待、首次通过、返工/冲突、测试耗时、资源和模型用量；不按生成代码量或活跃Agent数宣称效率提升。具体预算、观察窗口及扩缩阈值由执行计划登记，尚未实测，不伪称已提速。开发Agent并发不等于产品100条渲染同时执行。

### 7.3 方案取舍及仍须实证

已选动态队列调度；不采用固定实现者配额（空槽或审查积压时效率差），也不采用无限并发（超工具/资源上限并扩大返工）。保留有序依赖和共享基础单写；独立工作树隔离的是文件，不是语义或云权限。

调度原则已确认；N5a拒绝反例、工作树/资源隔离、实际槽位和模型路由、审查公平性、提交归因及合并后的正确性仍待验证。新会话启动与完整流程见14。当前只修订文档，不修改技能文件、Agent配置或CI。

## 8 工作树和资源隔离

所有并发写入任务使用独立worktree及唯一主题分支，助手创建分支默认codex/前缀。先复用合适隔离工作区，需新建时通过环境提供的工作树管理工具；路径由总控分配，任务卡绑定基线和允许范围。只有一个合格隔离工作区时降为单实现者串行；连一个都没有时停止代码实施，先解决隔离或另获明确的非SDD实施授权，不在原主分支直接开写。不假设子Agent自动获得私有目录。

重叠工作必须隔离，但worktree不解决语义冲突，也不是文件系统或云权限沙盒。Git的部分引用和配置仍共享，禁止任意改仓库/全局Git配置、他人分支、暂存区、工作树或历史。依据：[Git worktree](https://git-scm.com/docs/git-worktree)。

代码之外分别隔离临时库、测试账号/命名空间、端口、日志与产物、缓存及模型请求标识。显卡编码、Windows桌面、剪映应用实测由资源登记排队；只开不同目录不能避免这些冲突。测试环境不指向旧线上或真实用户资源；当前未授权创建任何环境。

## 9 Git提交归因和审计

C79要求提交可归因到对应Agent。建议：
- author记录真正贡献该提交的Agent身份；committer记录实际创建该提交的Agent、人或集成服务。代提交、重放、合并不能冒充原作者。
- 身份须使用项目批准的映射，不编造邮箱、人工姓名或签名，不改全局Git身份。尚无可用提交身份时先交付差异和证据，由总控解决，不伪造已提交。
- 优先保留原始Agent提交。多作者squash保留真实贡献者、任务及原始完整提交到合入提交映射；保留可访问的原提交引用，不能只留可能被清理的孤立hash。
- 在项目批准的提交尾注/PR台账登记Agent-ID、Task-ID、Baseline-Commit、Contract-Revision、Original-Commit及审查证据；model/effort和工具会话关联写入受控执行记录。只写实际发生的Reviewed-By或Co-authored-by，不制造确认。
- 实现者不能通过自改任务卡、门禁配置、验收基准或身份台账给自己扩大权限。

Git的author/committer/trailer是可填写的数据，不是强认证，也不能证明具体模型真的执行。可追溯须结合任务记录、提交差异、CI和审查；将来若需更强审计，再设计受控签名与追加记录，签名本身也不证明模型行为。

依据：[Git提交身份](https://git-scm.com/docs/git-commit#_commit_information)、[提交尾注](https://git-scm.com/docs/git-interpret-trailers)、[squash语义](https://git-scm.com/docs/git-merge)、[Git签名](https://git-scm.com/book/en/v2/Git-Tools-Signing-Your-Work)。本轮不执行commit、身份配置或签名配置。

## 10 合并门禁和串行集成

| 拟议必需门禁 | 必须挡住的反例 |
| --- | --- |
| 任务范围与所有权 | 越界修改、私改公共契约/迁移、修改自己的允许范围 |
| 格式/类型/依赖方向 | UI绕过应用接口、导入其他模块内部、混入供应商原始结构 |
| 契约和生成一致性 | 跨语言字段/时码不一致、必填被吞、旧消费者静默误读新版本 |
| 状态/授权/账本 | 非法跃迁、跨用户/绑定访问、Agent伪造人审、重复计费/退分 |
| 依赖与迁移 | 锁文件漂移、迁移编号竞争、空库/受支持旧版本升级失败 |
| 关键闭环与故障 | 保存重开丢轨、停止后假成功、断网占用被误释放、未知结果盲重传 |
| 安全与证据 | 密钥/素材混入Git、必需测试skip却显示通过、以旧测试报告代替当前差异 |
| 非作者审查与集成 | 自审自合、缺规格或质量结论、在过期基线通过就直接并入当前主线 |

门禁配置、任务分配登记及关键验收样例受独立保护；功能PR不能在同一改动内把自己的检查关闭后宣告通过。AGENTS/CODEOWNERS/本地钩子只提供指导或路由，必须结合实际分支保护、必需CI与非作者批准；远端能力未核验不能写成已配置。

集成顺序：基础契约与兼容层 → 依赖它的实现 → 跨模块回归。由一个集成负责人逐项合入最新集成基线，验证合并后的实际结果；两个分支分别通过不代表合并后通过。权限、迁移和发布的高风险范围保留人类负责人，合并不自动授权发布或旧版切换。

规格符合和代码质量必须分别审查。实现者自测不替代非作者审查，最终全分支审查不能由各模块“已完成”汇总代替。检查因环境原因未运行时写待验证，不标通过；没有实际验收证据不得进入已验证状态。

正式扩大并行前故意提交越界写共享文件、破坏旧消费者、跳过必测三类反例，确认真实门禁拒绝。不得只看到工作流文件存在就宣布已能防漂移。

### 10.1 审查角色和合入时点

同一位非作者可以分别给出规格符合、代码质量两项结论，必须分别记录；复杂风险按模型分级升级，不能只写一个笼统通过。总控若参与某项实现，不得成为其唯一审查者。审查者可以兼任集成者，但必须不是该变更的作者；集成解决冲突若产生新代码，也需另一个非作者审查。

任务审查通过可进入计划的隔离集成候选区，不等于进入main或发布。每个准备进入发布主线main的完整变更集，先在明确的候选合并提交上通过对应必需检查及全分支审查；合并队列只接受该PR头/集成头组合，任一前移需按6.1节重验。最终全分支审查在进入main之前，不是发布后的补手续；合并和发布仍是不同批准。

高风险范围的人类签核按4.1节，不能由不相干的普通代码审查替代。总控负责汇总证据、串行集成和状态登记，不凭“Agent已完成”豁免缺项。

### 10.2 按改动范围选择实测门禁

检查范围由受保护的影响规则及非作者审查决定，不由功能PR自己声明免测：
- 纯文档：结构、引用、决策覆盖和一致性检查；不要求无关媒体硬件跑一遍。
- 通用领域逻辑：相应单元、契约、权限/状态及跨语言样例；OS无关检查不宣称完成Windows验收。
- 触及Windows进程/路径/IPC、媒体时间线、worker、剪映适配或安装更新：合并前必须包含受影响的真实Windows构建/小样例或安装恢复证据。
- 小组发布：另跑已批准的完整支持矩阵、典型10/50/100条联合负载、目标硬件、剪映开改存重开、升级/恢复及新旧隔离。PR小样例不代替发布验收。

必需检查未运行就是未通过；真正不适用须由影响规则给理由并经非作者核对，不能用skip伪造绿灯。资源不足则等待所需验证，不用另一平台结果冒充。
