## 2 为什么是 pgvector（而不是向量库或托管 Supabase）

1. 素材主数据（账号、分类、标签、时长、时间）本来就要关系型存储与多条件过滤，把向量单独放到第二个存储会引入双写与一致性窗口。
2. 检索是「过滤 + 排序」混合型：`category1/2`、`video_type`、`labels &&`、时长区间、创建时间区间、`account_key`。pgvector 让过滤与近邻在同一事务快照里完成（`006_rpc.sql:82-99`）。
3. 托管 Supabase 无法 `shared_preload_libraries`，因此 zhparser / pg_jieba 这类需要预加载的中文分词扩展装不进去。结论是**不在数据库里分词**：应用层用 `@node-rs/jieba` 切好，写库时落 `tsvector` 列；再用 `pg_trgm` 兜住用户输入的半截词与错字（`003_indexes.sql:9-11` 的 `gin_trgm_ops`）。
4. 版本与能力已在本机实测固定：`vector` 扩展 `0.8.7`；`hnsw.iterative_scan=strict_order` 可设。后者是 HNSW + WHERE 过滤不漏结果的前提，缺它时过滤会退化成「先取 ef 个近邻再筛」，结果数不可控。

## 3 表与索引

### 3.1 扩展

| 扩展 | 位置 | 用途 |
| --- | --- | --- |
| `vector` | `001_extensions.sql:4` | 1024 维嵌入（`006_rpc.sql:57` 的 `vector(1024)`） |
| `pg_trgm` | `001_extensions.sql:5` | `ILIKE '%…%'` 与 `similarity()` 排序 |

`hnsw.iterative_scan` 是会话级 GUC，不是扩展；在每个检索连接上 `SET`。

### 3.2 表

| 表 | 角色 | 备注 |
| --- | --- | --- |
| `material` | 素材主表（供应商镜像） | `deleted_at` 软删；`labels text[]`；`duration_ms bigint` |
| `wiki_source` | 不可变证据层 | `content_hash` 有索引，同内容换模型版本可复用（`003_indexes.sql:26`） |
| `wiki_summary` | 纪要卡 + `embedding` | HNSW 建在这张表 |
| `wiki_entity` | Markdown 实体页 | `(company_key, kind, slug)` 唯一 |
| `wiki_edge` | 实体关系 | 两端各一条索引，外键不自动建反向索引 |
| `wiki_event` | 事件流（含仲裁） | 按 `(company_key, video_id, at DESC)` 查时间线 |
| `sync_state` | 同步水位 | 见 §5；`[实测]` ⑥ 校验了主键与存在性 |

`material.deleted_at` 为 `timestamp with time zone`（`[实测]` ⑦）。选软删而不是物理删，是因为素材可能在供应商侧恢复，且历史引用（wiki_source → material）不能断。

### 3.3 索引要点

- `material_name_trgm_idx`：`gin (name gin_trgm_ops)`。中文名称按空格分词效果差，三元组是一个与分词无关的兜底。
- `wiki_entity_kind_slug_uidx`：`(company_key, kind, slug)` 唯一。租户在最左，跨租户不可能命中同一条。
- `wiki_summary_embedding_hnsw_idx`：`hnsw (embedding vector_cosine_ops) WITH (m=16, ef_construction=64)`。参数是默认量级（`003_indexes.sql:26` 注释已写明），要按 recall 与内存实测再调，本文件不给固定值。
- `labels` 用 GIN 支持 `&&` 包含判断；`wiki_edge` 的两向索引是为了图遍历两个方向都走索引。

## 4 租户：三层，任一层都不依赖调用方自觉

1. **连接层 GUC**：`app.company_key`，每个请求由服务端设置，不由 SQL 参数决定（`006_rpc.sql:52`、`:139`、`:212`、`:268` 各函数首句读取）。
2. **RLS(force)**：六张表全部启用并对表所有者强制（`[实测]` ④：六张表 `rowsecurity` 全开）。`force` 意味着即使以表 owner 连接也受策略约束。
3. **函数内硬条件**：
   - 会话租户与入参不一致时**直接返回空集**，不报错——避免把「存在/不存在」变成探测通道（`006_rpc.sql:64-67` 的注释与 `IF`）；
   - 向量分支 `WHERE m.company_key = p_company_key`（`:85`）与 `AND m.deleted_at IS NULL`（`:86`）；
   - 关键词分支同样两条（`:109`、`:110`）。
   - 入参为空直接 `RAISE`（`:60-62`）。

`[实测]` ⑤ 覆盖了双租户互不可见与**跨租户写入被拒**（`infra/verify.mjs:127` 起以 `set role orange_app` + `set app.company_key` 构造）。

## 5 同步口径（智尚只读）

- **增量按天**：`esUpdate` 系列接口以天为粒度取「当日有变更」的集合，不做实时推送。
- **`lastModifyTime` 是死字段**：抽样 1000 条，1000 条全为 0。因此**不能**用它排序或做增量水位。
- **默认排序不是最新**：接口默认序与 `createTime` 无单调关系，翻页必须显式排序键，否则会漏/重。
- **越界页与空结果同形**：页码超过 `totalPage` 时返回 `total=0` + 空 `list`，与「真的没有数据」无法区分——分页循环不能用 `total==0` 判「无数据」，只能用「本页行数 < pageSize」。
- **单次日增量成本**：`ceil(行数/200)` 页 + 1 次 token 获取（`pageSize` 固定 200 时）。
- **限流**：1 QPS、并发 1；失败退避 2/4/8/16/32 秒，最多 5 次；不并发重试。
- **水位推进时机**：整页落库成功之后才写 `sync_state`；半页失败留在原地重来，宁可重复不可丢。

## 7 检索函数的两条分支（读 `006_rpc.sql`）

函数头（`:48-49`）：`SECURITY INVOKER` + `SET search_path = public, pg_temp`。用 INVOKER 而不是 DEFINER，意味着**调用者的角色权限仍然生效**——RLS 因此不会被函数的属主身份绕过。`search_path` 固定是为了防止调用方在同名 schema 里放影子对象。

| 步骤 | 行为 | 位置 |
| --- | --- | --- |
| 会话租户 | `current_setting('app.company_key', true)` 读不到时为空 | `:52` |
| 参数钳制 | `limit` 夹到 `[1,100]`，默认 20 | `:55` |
| 空入参 | `p_company_key` 空即 `RAISE`（22023） | `:60-62` |
| 租户不符 | **直接 `RETURN` 空集**，不报错 | `:64-67` |
| 分支选择 | `filters ? 'embedding'` 决定走向量分支 | `:57-58` |

### 7.1 向量分支

排序是 `ORDER BY s.embedding <=> v_vec, m.video_id`（`:98`）：余弦距离升序，**第二排序键 `video_id` 用于稳定输出**——距离相等时顺序不会随执行计划抖动，翻页与快照可比。

过滤条件（`:88-97`，全部是 `AND`）：

| 条件 | 语义 |
| --- | --- |
| `m.name ILIKE '%'||v_query||'%'` | 名称子串（走 trigram GIN） |
| `category1` | 一级分类等值 |
| `category2` | 二级分类 `= ANY(array)`（多选） |
| `video_types` | 视频类型多选，`::smallint[]` |
| `labels && v_labels` | 标签数组有交集 |
| `min_duration_ms` / `max_duration_ms` | 时长区间 |
| `created_from` / `created_to` | 创建时间区间，上界按 `+ interval '1 day'` 补到天末 |
| `account_key` | 按供应商账号过滤 |

`filters` 里任何一项为 `NULL` 即视为不过滤（`IS NULL OR …` 写法），所以同一个函数能覆盖「只检索」与「检索+任意组合筛选」。

### 7.2 关键词分支

`:103-110`：`score` 用 `similarity(m.name, v_query)`，无查询词时固定 `0::real`（避免 `similarity(NULL)` 影响排序）。租户与存活两条硬条件与向量分支完全相同（`:109-110`）——**两条分支不允许出现不同的可见性口径**，这是改动时必须一起改的地方。

### 7.3 为什么「返回空集」而不是「报错」

`[代码]` `:64-67` 的注释写明：调用方给不出别的租户时返回空集，避免把「存在/不存在」变成探测通道。代价是调用方无法区分「无权限」与「无数据」；这是有意的取舍，排查时需要看服务端日志而不是看返回值。

## 8 改动检查清单

改 SQL 或同步逻辑前后，按这个顺序确认（每条都对应上面的硬条件）：

1. `infra/verify.mjs` 8/8 通过；
2. 新增查询是否把 `company_key` 放在最左、是否仍带 `deleted_at IS NULL`；
3. 新增索引是否以 `company_key` 开头（否则 RLS 过滤后走不到索引）；
4. 向量分支与关键词分支的硬条件是否仍然逐条一致；
5. 同步水位是否仍在「整页落库后」推进；
6. 分页终止条件是否仍以「本页行数 < pageSize」判定，而非 `total == 0`。
