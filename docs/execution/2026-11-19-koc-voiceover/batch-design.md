# 批量出片：Fission 原生逻辑 vs 我们的计划，以及"100 条"到底怎么来

日期 2026-11-19 · 与 `playbook.md`、`openfilm-capabilities.md` 配套

> 这一页要回答的是：**同一套素材/配音/BGM，怎么出 100 条**；以及原来那套混剪逻辑（顺序交叉、随机）在我们
> 的新链路里保不保得住。结论先说：**两种"100 条"必须分开**，一种交给 Fission 的批量参数，另一种必须由我们
> 展开成 100 份计划 —— 混着做，出来的片子会既不可控又不好看。

---

## 1. Fission 原生的批量语义（读代码得到的，不是猜）

| 字段 | 语义 | 对"100 条"的含义 |
|---|---|---|
| `Count` | 生成数量上限；**与配音池耗尽先到先停**（0 = 不限） | 100 条就是这个池子被用完为止 |
| `AudioUses` | **每个配音最多用于几条成片**（1 = 用一次就弃，0 = 不限） | `AudioUses=1` + 100 个配音 = 100 条各说各的；`AudioUses=0` + 1 个配音 = **同一个配音剪 100 遍** |
| `PickRule` | `SceneOrderRandomWithin`（组内随机）/ `Random`（全池随机）/ `Sequential`（按序） | 决定"每条成片的素材顺序是否不同" |
| `GroupRule` / `SceneGroups` | 场景组：先按组顺序取，组内再随机 | 这就是"**按顺序交叉混剪**"：组与组之间有序，组内打散 |
| `SplitMode` | 场景切分 / 平均 N 片 / 按秒 / 随机区间 / 不切 | 决定一个素材被切成几刀参与混剪 |
| `BgmDir` / `BgmVolume` | 一个 BGM 目录，一条成片配一个 BGM | **单条只能一个 BGM**；批量换 BGM 只能靠"多条成片各取一个" |
| `IntroDir` / `OutroDir` | 固定片头/片尾池 | 每条成片取一个 |
| `GeneratedAudioCount/Duration` | 没有 AudioDir 时离线合成配音 | 我们不用（配音由 TTS 真实生成） |

**一句话**：Fission 的批量 = **同一个声音骨架 × 素材池随机重组**。它擅长"一条配音出 100 个剪辑版本"，
它做不到"100 条各自不同的文案"。

---

## 2. 三种"100 条"必须分开

| 类型 | 是什么 | 谁来做 | 例子 |
|---|---|---|---|
| **A. 变体**（Fission 原生） | 同一文案/配音，素材与顺序不同 | **Fission**：`Count=100`、`AudioUses=0`、`PickRule=SceneOrderRandomWithin` | 同一条小青柑口播，100 个剪辑版本挑一个投 |
| **B. 矩阵**（我们的） | 文案、配音、BGM、开场都不同 | **我们**：展开成 100 份 `plan.json`，每份跑一次 job（`Count=1`） | 6 个场景 × 4 种文案 × 4 段配音 ≈ 96 条 |
| **C. 规格**（我们的） | 同一内容，多平台/多时长 | **我们**：每个规格一份 plan | 15s 竖屏 + 30s 横屏 + 60s 口播 |

我现在的 `plan.json` 是 **B 里的一条**。要出 100 条，缺的不是 Fission 的参数，而是**一层展开器**（第 3 节）。

## 3. 缺的那一层：`planset.json`（变体矩阵 → N 份 plan）

```jsonc
{
  "schema": "orange/planset/1",
  "id": "xqg-100",
  "base": { "id": "xqg", "lines": ["过完年，饭局有点多", "…"], "spec": { "targetSec": 15, "aspect": "9:16" } },
  "axes": {
    "copy":     [ { "hook": "过完年，饭局有点多" }, { "hook": "开箱那一下，我就知道选对了" } ],
    "voice":    [ { "provider": "qwen", "voice": "Cherry" }, { "provider": "minimax", "voice": "female-shaonv" } ],
    "bgm":      [ "library:music/xxx", "library:music/yyy", null ],
    "materials": { "pool": ["48135993", "50033909", "40280102", "…"], "policy": "no-repeat-across-batch" },
    "order":    ["as-written", "hook-first"]        // 句子顺序的两种排法
  },
  "expand": 100,
  "dedupe": {
    "material": { "acrossPlans": "no-repeat", "withinPlan": "no-repeat", "fallbackMaxReuse": 3 },
    "bgm": { "adjacentDifferent": true },
    "voice": { "maxPlansPerVoice": 50 }
  }
}
```

展开规则（`expandPlans(planset)`）：

1. 对每条轴做**笛卡尔积**，得到候选组合（可能远大于 100）；
2. 按 `dedupe` 过滤：素材跨条不重复 → 池子不够时按 `fallbackMaxReuse` 放宽**并如实记 `shortage`**；
3. 用确定性选样（`md5(plansetId + index)`）而不是真随机 —— 同一份 planset 两次展开结果相同，出问题能复现；
4. 每条产出一份 `plan.json`（含自己的 cues、配音、BGM、素材分配），之后**各跑各的 job（`Count=1`）**。

这样"100 条"里每一条都是可复核的：谁的文案、谁的配音、用了哪几条素材、时长多少、合规过没过。

## 4. 复用规则（对应你问的三件事）

| 东西 | 单条内 | 跨条 | 为什么 |
|---|---|---|---|
| **视频素材** | 不重复（同一素材在同一条里出现两次很显眼） | 默认**不重复**；池子不够时允许"至多 k 条共用一条素材"，并报 shortage | 100 条用同 5 条素材，观众连着看会认出来 |
| **BGM** | 只有 1 个（Fission 的 job 只认一个 BgmDir） | 可复用，但**相邻两条不同** | BGM 重复不刺眼，但连播两条同曲会出戏 |
| **字幕** | 来自该条 plan 的 cues | **绝不共用** | 文案不同，字幕必然不同；共用就是错的 |
| **配音** | 该条自己的 TTS 产物 | 只有"同一句文案的变体"可以共用（省 TTS 成本），`AudioUses` 语义 | 不同文案共用配音 = 音画对不上 |
| **元素（转场/贴纸）** | 按场景标签取 | 可复用 | 元素是风格的一部分，复用是好事 |

## 5. 你提的两点，我的回应

**① 缩略图复用 Studio 的素材缩略图** —— 同意，而且这是更合理的默认：

- 批量列表里给人看的是"这条用了哪些素材"，**素材缩略图**正好回答这个；
- 渲染首帧只有出片之后才有，而列表要在出片前就给人看；
- 折中：列表先用素材缩略图（`MaterialCard` 的 cover/thumb），出片后在后台把这张换成真实首帧并缓存，
  下次打开看到的就是准确的。

**② Fission 的输入可以是本地文件或云管家素材** —— 对，我们的桥接层已经把两者统一：

```
云管家素材 → materials.take → <project>/assets/<名字> (<id>).mp4  ┐
本地文件   → 用户直接放进 assets/（或在 Studio 里拖进来）           ├→ staging 目录（按计划顺序命名）→ Fission
```

差别只在"取用"这一步，Fission 那侧看到的永远是 `assets/` 下的文件。所以**不需要给 Fission 加"云管家"概念**。

**③ 进阶设置做成折叠** —— 同意，而且我建议明确分层：

| 层 | 放什么 | 谁改 |
|---|---|---|
| 默认层 | 预设（抖音竖屏 15s）、批量条数、素材池、BGM 池、按钮 | 运营 |
| 进阶（折叠） | `SplitMode`/`AlignStrategy`/`Threads`/`VoiceVolume`/`BgmVolume`/`SceneGroups`/`AudioUses`/`PickRule` | 技术/主管 |
| 隐藏（配置文件） | `GeneratedAudio*`、`NamingRule` 细节 | 我们 |

## 6. 需要你拍板的三件事

1. **100 条以哪种为主**：A（同配音 100 个变体）、B（文案×配音×BGM 矩阵）、还是 A×B（先出 10 个文案，每个再变 10 版）？

2. **素材池怎么来**：一次检索的前 N 条，还是给人一个"选池"的界面（多选素材成池）？我建议后者，池子可命名复用。
3. **跨条素材去重的严格度**：`no-repeat`（100 条用 100 组不同素材，需要 ≥600 条素材）还是 `至多 k 条共用`（默认 k=3）？
   按我们语料 67 156 条，`no-repeat` 完全撑得住，但它会逼着检索每次给不同结果 —— 检索要支持"排除已用"。

## 7. 修订：文案 / 配音 / 字幕是一个整体（2026-11-19 追加）

你的判断对，而且这条比我原来的写法更准：

```
文案（说什么） + 配音（谁念、什么音色） = 「一条 take」（一个说话单元）
字幕 = 从 take 的句子 + 镜头时长**派生**出来的，不是一根轴
BGM = 独立轴（但要受"情绪/场景"约束，不能纯笛卡尔）
素材 = 每个来源池各是一根轴（多素材目录 = 多根轴）
```

**为什么字幕不能是轴**：cue 的时间 = 句子 + 镜头显示时长。它由 take 与排片共同决定，
让人去挑"用哪份字幕"只会挑出与前两者不一致的组合 —— 那正是"音画对不上"的来源。
所以字幕永远是**算出来的**，不给选择。

**为什么配音可以单独变化但仍属于 take**：同一句文案换音色（女声/男声/方言）是常见的 A/B，
但它必须和文案绑在一起走（文案改了就得重录）。所以：

```
takes = 文案 ⊗ 音色        （文案 V 个 × 音色 W 个 = V×W 条 take，每条自带 cues）
```

## 8. `planset.json` v2（多素材池 = 多轴）

```jsonc
{
  "schema": "orange/planset/2",
  "id": "youqi-oulong-100",
  "product": { "name": "油弃乌龙茶", "scene": "办公" },
  "spec": { "targetSec": 15, "aspect": "9:16", "minShots": 5 },

  /* 一根轴：文案；另一根轴：音色。两者相乘 = takes，cues 由 take+排片派生 */
  "copy": [
    { "id": "hookA", "lines": ["过完年，饭局有点多", "下午那杯是我的开关", "…"] },
    { "id": "hookB", "lines": ["开箱那一下，我就知道选对了", "…"] }
  ],
  "voices": [
    { "id": "qwen-cherry", "provider": "qwen", "voice": "Cherry" },
    { "id": "minimax-shaonv", "provider": "minimax", "voice": "female-shaonv" }
  ],

  /* 多素材池：每个来源目录/检索结果各一根轴，并声明它填哪一类镜头位 */
  "pools": [
    { "id": "main",    "from": "search:小青柑 冲泡 特写", "fills": ["S1", "S3"], "order": "sequential" },
    { "id": "pack",    "from": "folder:D:/dev/sucai/油弃乌龙茶/包装", "fills": ["S2"], "order": "random" },
    { "id": "broll",   "from": "search:小青柑 晒场 空镜", "fills": ["S4"], "kind": "broll" },
    { "id": "reaction","from": "folder:D:/dev/sucai/油弃乌龙茶/人物", "fills": ["S5"], "order": "random" }
  ],

  "bgm": { "pool": ["library:music/warm-strings", "library:music/light-electronic"], "mood": "办公" },

  /* 展开：不是全笛卡尔（5 轴 × 10 会是十万），而是"按轴排序采样 + 约束" */
  "expand": 100,
  "sample": "deterministic",            // md5(plansetId + index)，同一份两次展开结果相同
  "dedupe": {
    "material": { "acrossPlans": "no-repeat", "withinPlan": "no-repeat", "fallbackMaxReuse": 3 },
    "bgm": { "adjacentDifferent": true },
    "take": { "maxPlansPerTake": 50 }
  }
}
```

展开顺序（决定"100 条"里的多样性来自哪）：

```
1. 先定 take（文案 ⊗ 音色）：让每条片子的"说法"先散开
2. 再按池轮转素材：同一 take 的不同成片换素材，而不是换说法
3. 最后定 BGM：只在该场景的候选里轮转，相邻两条不同
→ 结果：100 条里既有不同说法（take），又有同一说法的不同剪辑（素材轮转）＝ A×B 的混合
```

**为什么不是纯笛卡尔**：5 根轴每根 10 个选项 = 10 万组合，而你要的是 100 条。
纯笛卡尔会产出"同一说法 + 同一素材 + 只换了 BGM"的近似重复；按上面三步采样，
100 条里的差异落在**说法**与**剪辑**两处，这才是观众能感知到的不同。

## 9. 新增一块能力：本地素材目录入库

你说的 `D:\dev\sucai\油弃乌龙茶` 这种目录，现在的链路还接不上（`assets/` 里只认已有文件）。
需要补一个 `materials.import`：

```
输入：一个绝对目录
做：ffprobe 每条（时长/分辨率/有没有音轨）→ 生成条目（id = 目录内相对路径的稳定哈希）
    → 复制或硬链进 <project>/assets/<池名>/<原名>.mp4
    → 写进 pool 定义（planset 里 `from: "folder:…"` 解析成这批 id）
限制：只读目录；不认识的编码先转码（或用 ffmpeg 的 copy 流）
```

有了它，"本地素材"与"云管家素材"在 planset 里就是同一种东西：**一个池**。

## 10. "池子足够大"之后要解决的问题：取哪 100 条（2026-11-19 追加）

operator 的判断成立：

```
A×B×C×D×E×n（5 轴 × 每轴 10 个）= 十万级组合
只取前 100 条 → 数学上不可能重复
```

所以"池子够不够大"这个疑问可以划掉。剩下的问题是**感知差异**，两件事：

### ① 别让弱轴吃满组合数

组合空间里各轴的"观众感知权重"并不相等：

| 轴 | 感知强度 | 说明 |
|---|---|---|
| 说法（take = 文案⊗音色） | **最强** | 换一句话，观众立刻觉得是另一条 |
| 素材组合 | **强** | 同一句话换个画面顺序，也看得出来 |
| 开场镜头（前 3 秒） | 强 | 决定划不划走 |
| BGM | 中 | 换曲子能感觉到，但不会觉得"另一条片子" |
| 贴纸 / 文字版式 | 弱 | 几乎不影响观感 |

如果按"下标从 0 递增"机械展开，最外层往往是弱轴（BGM），于是前 100 条里会出现
**“同一说法 + 同一素材 + 只换了 BGM”**的近似重复 —— 空间够大，但选得不好。

所以采样按**强轴优先**分层：

```
第 1 层轮转：take（说法）           —— 100 条至少要 N_take 种说法（建议 ≥10）
第 2 层轮转：素材池组合（每池轮流取，跨条不重复）
第 3 层轮转：开场镜头（hook 池）
第 4 层才轮到：BGM（相邻不同）
最后一层：贴纸/版式（几乎可以固定）
```

等价于：**把组合空间按"感知差异"排序，取前 100**。这样 100 条里既有不同说法（强轴散开），
又有同一说法的不同剪辑（素材轮转）—— 这才是"看起来是 100 条"。

### ② no-repeat 要靠"一次取够候选"，不是每次问检索

100 条 × 5–6 镜 = **500–600 个镜头位**。跨条不重复素材 = 需要 600 条不同素材。
我们语料 67 156 条，撑得住 —— 但前提是**别一条一条去检索**：

```
错：for i in 1..100 { search(query) → 取前 6 条 }      // 100 次检索会撞车，而且慢
对：search(query, limit: 600) → 分配器统一切片          // 一次取够，按池配额分给 100 条
```

所以 planset 展开前要做一次**配额计算**：

```
每个池需要的素材数 = Σ(该池负责的镜头位 × 条数) ÷ (跨条去重放宽系数 k)
若 池容量 < 需求 → 提前报 shortage（"pack 池只有 40 条，100 条片子需要 100 条"），
                    而不是展开到第 60 条才发现没素材
```

这条和我们已有的 `plan.create → shortageSec` 是同一套诚实原则：**提前说缺，不硬凑**。

## 11. 更正：判据不是"观众感知"，是**多层指纹**（2026-11-19 追加）

我上面用"观众感知差异"来排序组合，这个判据是错的 —— **平台不是看画面像不像，是比多层指纹**。
公开资料里的主流描述是六层级联（任一层命中就可能被标记为重复内容）：

| 层 | 比什么 | 我们这边对应哪根轴 |
|---|---|---|
| ① 文件层 | MD5/SHA1、容器元数据、编码器指纹、码率/帧率 | 每条独立渲染（天然不同）+ 导出参数抖动 |
| ② 视觉层 | 关键帧 pHash/dHash、Hamming 距离 | **素材组合**、裁切/缩放、调色、画中画 |
| ③ 时序层 | 帧序列指纹、运动轨迹、**镜头切换节奏** | 镜头时长、切点、转场选择 |
| ④ 音频层 | 频谱峰值指纹（类 Chromaprint）、**ASR 转文本** | **配音**（必须重新合成，不能复用同一音频文件）、BGM |
| ⑤ 深度层 | CNN/CLIP embedding 余弦相似度 | 素材语义、整体画面构图 |
| ⑥ 跨模态 | 以上投票融合 | 上面五项都不撞才有意义 |

要点（来源见文末）：

- **改画面只能骗过 ②**；语义与结构不变、音频不变，依然判重复 —— 所以"只换 BGM""只调色"是无效差异；
- **同一条配音复用是最致命的**：ASR 转文本后，文本向量几乎相同；
- **封面单独一层**（pHash），所以 100 条的封面必须来自不同镜头；
- 平台具体阈值不公开，也没有"保证不被查重"的做法；我们能做的是**每一层都真的不同**，并且**自己能算出来**。

### 于是轴的权重重新排（按"能破坏哪几层"）

| 轴 | 破坏的层 | 结论 |
|---|---|---|
| 文案（take） | ④ ASR 文本、⑥ | 必须真的改文案，不是只换音色 |
| 配音（重新 TTS） | ④ 频谱指纹 | 每条独立合成；同一句文案的变体也不能共用同一个音频文件 |
| 素材 + 剪辑节奏 | ②③⑤ | 素材组合 + 镜头时长 ±0.3–1s + 切点变化 |
| 裁切/缩放/调色/画中画 | ②⑤ | 每条给一组轻微不同的参数（不是一键套滤镜） |
| 封面 | ② 封面 pHash | 每条取不同镜头的帧 |
| 标题/话题/字幕文本 | 文本层、⑥ | 标题模板轮转；字幕由文案派生（本来就会变） |
| 导出参数 | ① 文件层 | 帧率/码率轻微不同（29.97 / 30 / 50） |
| BGM | ④ | 独立轴，相邻不同 |

### 新增：本地预检 `dedupe-check`

发布**之前**，我们自己算 100 条的层间相似度，而不是等平台告诉我们：

```
每条：md5、关键帧 pHash（3 帧）、镜头时长序列、音频频谱指纹摘要、ASR 文本
两两比：pHash Hamming、时长序列编辑距离、音频指纹 Jaccard、文本余弦（本地向量即可）
输出：矩阵 + 需要重做的条目（"第 12 条与第 7 条音频层 0.93、文本层 0.88"）
```

这一步不承诺"过审"（阈值不公开），但保证**不会拿近似重复的 100 条去撞墙**。
