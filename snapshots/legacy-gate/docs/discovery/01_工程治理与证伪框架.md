状态：讨论稿 v0.29。日期：2026-11-05。此框架提出评审对象与质量门槛，不表示相关工具、云配置或 CI 已部署。

## 目标与非目标

目标是让需求、模块、契约、代码、测试、问题和发布有同一条证据链，而不是靠口头记忆或不断增加工具。当前不开发产品、不创建 Supabase 表或权限策略、不迁移旧数据、不安装参考项目依赖。

不承诺绝对无故障或绝对安全。可靠性、安全性和鲁棒性需要可测目标、失败处理以及恢复验证；目标硬件档位已明确为 i5 / 16 GB / GTX 1660 Ti 及以上；性能和恢复阈值仍需基于具体处理器型号、素材负载与真实测试结果确定。

## 新旧版本隔离

C48已确认：本轮重构与现有已上线方案分开，不影响旧线上服务、数据、配置和用户。本阶段仍只维护方案文档。后续工程建议：独立开发/测试环境、数据库或明确的数据隔离、存储位置、本机应用标识/数据目录和发布通道；验证新版安装/卸载/升级不覆盖旧版文件与配置。不得使用指向现网的默认连接执行试验迁移。

旧账号和历史数据迁移先形成可恢复副本上的核验方案；读取或复制真实数据也须明确范围。生产写入、流量切换、旧版替换和停用须单独授权，PRD评审不授权自动切换；备份和回滚演练不能影响旧版正常运行。

## 代码风格与契约规范建议

统一的是语义和质量标准，不强迫所有语言使用同一种语法风格。

- TypeScript：严格类型检查、稳定的模块边界、格式化和静态检查。
- C#：使用语言原生格式化/分析器，约束异步取消、空值、资源释放。
- Python：格式化、静态检查、关键边界类型与输入验证。
- 工具选择倾向跟随上游和现有生态，具体配置在技术选型后锁定；不同时启用相互冲突的格式化工具。
- 所有语言共享命名字典、错误分类、时间单位、状态机和契约测试样例。
- 格式化生成文件不手改；契约生成应可重复，CI检查生成差异。
- 领域实体不从UI对象反向推导，数据库表不由每个worker自行命名和创建。
- 契约变更需声明向后兼容性；breaking change 必须有版本、迁移及旧客户端处理策略。
- 本地IPC也按不可信输入验证；媒体路径、URL、外部程序参数不由模型输出直接拼接执行。

## Git 与提交规范建议

- main 代表可发布基线，不允许直接堆未评审的大改。
- 使用短生命周期主题分支；本助手创建的分支使用 codex/ 前缀。
- 每次提交聚焦一个目的，不把格式化、契约迁移和功能重写混在一起。
- 建议采用 Conventional Commits：type(scope): description。
- 建议 type：feat、fix、refactor、test、docs、build、ci、chore；scope 使用 auth、materials、ingest、fission、editor、export、contracts、workers、observability 等受控词汇。
- 不兼容变更标记 ! 或 BREAKING CHANGE，正文解释迁移影响；中文或英文描述均可，格式统一。
- 本地提交钩子不是安全边界，关键规则必须在 CI 再检查。
- 密钥、运行数据、素材文件、工具缓存和不经审核的诊断包不得默认进入 Git。
- 归档副本不等于可发布的干净 Git 基线；首次提交前检查暂存区和秘密扫描，避免直接 git add 全目录。

依据：[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)。

## PR 规范建议

每个 PR 说明：
1. 关联需求、问题或 ADR。
2. 改了什么、明确没有改什么。
3. 契约、权限、数据库与兼容性影响。
4. 验证命令、样例、结果和未覆盖范围。
5. 数据迁移、失败处理与回滚/前向修复方案。
6. UI或媒体行为变化的可检查证据。

建议至少一名非作者审阅；AI审阅作为辅助，不替代关键权限及发布的人类负责。大改先拆出可验证边界，不按任意行数机械拆分。

main 需要实际配置保护规则和必需检查，而不只在文档中声明。私有仓库是否能使用对应保护能力需按账号计划确认。关键测试被跳过不得被误认为已验收；聚合门禁应验证必需测试实际执行。[GitHub分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## CI 与 CD 分开设计

### PR 合并前

候选阻塞项（按09第10.2节的改动影响矩阵选择，必测不得skip；纯文档不强制无关实机，触及Windows/媒体边界须真实目标环境证据）：
- 格式、静态检查、类型检查。
- 单元、契约、跨语言序列化测试。
- 身份、RLS、小组隔离、非法状态转换测试。
- 关键业务闭环与小型媒体样例测试。
- 从空库迁移及从受支持旧版本升级测试。
- 依赖锁、秘密扫描、依赖与许可证审查。
- 首版客户端只支持 Windows，构建、安装、媒体闭环与升级恢复必须有真实 Windows 验证；Linux 上的通用逻辑检查不能替代这些证据。先在 Ethan 本机 i7 / RTX 4060 / 32 GB 上验证功能与稳定性，后续再在 i5 / 16 GB / GTX 1660 Ti 目标档位验证；记录实际处理器型号、Windows、磁盘与显卡驱动。本机通过不代表目标档位性能已通过；不增加 macOS/Linux 客户端发布门禁。

资源门槛建议：先在本机记录客户端、Fission、ASR及导出的联合负载，再到 16 GB 目标测试机验证资源预算；采用有界并发和前台预览优先的调度。限制本机可用内存不能代替低配实机验收。未测定前不承诺具体并发数、处理速度，或所有任务同时执行仍无卡顿。

典型媒体样例：按10/50/100条批量覆盖，使用3–5秒素材，生成30–45秒及45–60秒成片；已确认默认输出为1080×1920（宽×高）、30fps、9:16竖屏。首版正式导出分辨率为720p/1080p，竖屏基准用例必须覆盖720×1280与1080×1920；4K不纳入首版发布验收，并验证超出支持范围的请求被明确处理，而非静默降级。输入规格差异、边界时长和异常媒体另设样例，不能把典型范围写成未获确认的拒绝规则。

### 小组测试发布

候选发布门槛：
- 明确的版本与源码commit关联、依赖/worker/媒体引擎清单。
- 签名、安装、更新、旧版本升级与回退验证。
- 目标剪映版本的打开、编辑、保存、重开测试。
- 环境隔离：开发/测试不使用生产凭据与真实敏感样本。
- 合并代码不自动发布给全部用户；首版小组灰度与人工发布确认。
- 数据库变更采用兼容旧客户端的演进，回退应用不等于可以安全回退数据。
- 备份恢复演练覆盖数据与文件，不把数据库备份误认为媒体文件备份。

## 问题埋点、日志、追踪和审计

C51确认首版必须覆盖性能和错误埋点、标准化日志、追踪与审计；以下具体工程机制仍待验证，不代表现有工具已经配置。

| 类型 | 目的 | 要求 |
| --- | --- | --- |
| 运行日志 | 诊断故障 | 结构化、分级、限量、轮转；可采样 |
| 链路追踪 | 关联跨UI、进程与云端调用 | traceId/spanId，并关联jobId、attemptId与资源版本 |
| 产品事件 | 理解用户任务和功能使用 | 有事件字典、用途、采集边界及隐私选择 |
| 业务审计 | 解释授权、审核、共享、撤销和发布 | 可信端记录、不可由普通客户端改写；关键事件不采样 |
| 用户问题反馈 | 将具体投诉关联到技术证据 | issueId、版本、错误码、发生时间、任务/追踪引用及可预览脱敏诊断包 |

建议公共日志字段：timestamp、severity、eventName、service、component、environment、appVersion、buildCommit、traceId、spanId、jobId、attemptId、errorCode、durationMs。不存在的上下文字段省略，不制造伪标识。

涉及用户或资源的标识按需要脱敏，并限制访问。禁止默认记录token、企业密钥、签名URL、完整本地路径、原始字幕、素材内容或完整模型输入输出。错误堆栈也必须经过脱敏。

日志相关字段参考 [OpenTelemetry日志模型](https://opentelemetry.io/docs/specs/otel/logs/data-model/)。业务审计另加 actor、action、objectVersion、approvedScope、outcome、reason 等语义，不把通用服务日志当作审计账本。

本地离线记录不等于可信云端审计：标注来源与待同步状态，不伪装成已由服务端确认。追加写、受限写权限、保留策略和完整性校验用于降低篡改风险，不宣称数据库管理员绝对无法篡改。

诊断日志可按经批准的保留期轮转；C58公司业务操作记录不删除，按归档/查询、受控访问和恢复设计，不能用通用删除策略清除。具体诊断保留期、访问范围和成本预算待工程提案/评审。

### 性能与错误事件字典

C51已将本节能力纳入首版要求，具体覆盖见[PRD第10节](D:/dev/orange/docs/06_橙子生产级重构PRD.md)。每个功能登记事件名/版本、目的、开始结束边界、耗时单位、结果类别、字段隐私、采样和责任人；排队、执行、外部等待分开，成功/失败/取消/拒绝/未知各有分母，关注分位延迟而非只看平均。

覆盖素材检索下载、加工及AI阶段、编辑首帧/定位/预览/保存、混剪规划/准入/渲染、视频与剪映交付、云上传逐项核对、模板/技能保存应用，以及CPU/GPU/内存/磁盘/进程崩溃。重复组合、无数据和取消不是系统崩溃；HTTP200不等于业务成功。

事件字段和错误码在07登记，应用、worker和服务共用语义。高频拖动/逐帧事件聚合或限量，不无界写业务库；用户/工程/任务ID不作高基数指标标签。统一日志增加schemaVersion/requestId及适用的对象修订关联，不能打印全部payload。

### 可靠记录与治理边界

创作记录与公司知识资产是业务数据，不依赖可采样运行日志重建。关键审计不采样，受控追加、更正留痕；本地待同步与可信服务事实分开。关键副作用必须可靠保留必要批准/账务记录，具体事务、发件箱及补登记机制待验证；普通监控失败不阻塞剪辑。C40已准入任务仍可本地持久留证并交付，不增加终态联网门槛。

按用户隔离缓存和上报队列，限制诊断访问并脱敏；日志轮转、缓冲/重试和存储有界，统计普通遥测丢弃情况。采集目的不自动扩展为员工监控或模型训练，确认技能保存不等于确认外发原工程和媒体。C52/C53确定公司管理员可查看管理本公司的沉淀资产，员工离职后公司保留；C55要求团队共享另有人工确认。目录/必要同步、管理角色和动作、离职交接、归档与误删防护按D08/D24，C58明确公司业务操作数据不删除，不扩张到全部原工程/媒体。

### 公司治理与人工确认的验收补充

C52–C55的实现需覆盖：本公司管理员权限及其授予/撤销验证、查看/管理审计、普通同事不可见和跨公司拒绝；员工停用不级联删除公司沉淀资产，保留创建者/版本/确认来源，交接/备份能恢复；LLM候选到人确认的状态变化；团队共享确认绑定内容版本和团队，不因沉淀确认/离职/管理员查看自动生效。

LLM调用按统一AIInvocation/Job记录输入引用、提示词/模型版本和输出候选，不将全文打进日志；错误或未知不伪造确认。管理员管理也不能让模型自审或无痕覆盖来源。共享变更和撤回应核验有效范围并使相关缓存/索引按策略失效，角色回收后不能靠旧缓存绕过。具体机制和V28–V30仍未验证，本轮不执行真实模型调用或采集。

### 执行授权 IP撤回与公司留存验收

C56确认请求批准/全权限两种执行模式，四类人工最终确认不被替代。审计区分授权人、实际执行主体、自动检查与真实人审，不由Agent回执伪造人确认。验证授权收回、作用范围变化、提交冲突和重试，不能由全权限扩大账号或素材/IP权限。

C57确认对应账户撤权后不可见、不可再请求。验证搜索/列表/直链/缓存/代理/转写/历史工程/模板/Agent的共同限制、在途结果隔离、备份恢复不复权。离线设备的撤权传播时效和系统外文件不可追回是需明确评审的限制，不宣称已实现即时撤权；C40仅在授权有效时适用。

C58确认公司保留全部业务操作数据，不删除；覆盖任务、编辑修订、选材记录、审核批准、交付、积分及来源链。普通诊断日志采样/轮转、清缓存或账号撤权不得删除业务记录；本地待同步、公司核验留存和可恢复备份分别验证。公司留存不等于全量原始媒体同步，不扩大受限用户或管理员访问。
